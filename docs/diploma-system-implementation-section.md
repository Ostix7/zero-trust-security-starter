# Розділ 4. Реалізація системи Zero Trust Starter для Spring Boot мікросервісів

## 4.1. Мета розділу та загальний підхід до реалізації

Після визначення архітектурних принципів і функціональних вимог наступним етапом є формування підходу до реалізації системи Zero Trust Starter для Spring Boot мікросервісів. Якщо попередній розділ був присвячений проєктуванню цільової архітектури, то в цьому розділі деталізуються технологічні засоби, структура проєкту, спосіб організації модулів, механізми взаємодії між ними та практичні аспекти інтеграції starter-а в прикладний мікросервіс.

Основна мета реалізації полягає у створенні повторно використовуваного програмного компонента, який може бути підключений до будь-якого Spring Boot сервісу як залежність і після цього автоматично активує набір узгоджених механізмів безпеки. При цьому розробнику не потрібно вручну відтворювати базову конфігурацію JWT Resource Server, налаштовувати однакові обробники помилок, писати фільтри аудиту, додавати інтерцептори для прокидання токенів або перевіряти очевидно небезпечні налаштування. Уся ця логіка має бути зосереджена всередині starter-а та вмикатися через автоконфігурацію.

З практичної точки зору система реалізується як багатомодульний Maven-проєкт, у якому функціональність розділяється за відповідальністю. Такий підхід дає змогу поетапно нарощувати можливості starter-а, підтримувати слабке зв’язування між окремими частинами рішення та спростити тестування кожної підсистеми. Оскільки Zero Trust охоплює різні аспекти безпеки, від валідації токенів до контролю роботи із секретами, реалізація однією монолітною бібліотекою була б менш керованою і гірше масштабувалась би під реальні потреби команд.

У межах цього розділу реалізація системи розглядається як комбінація трьох складових. Першою складовою є базовий каркас starter-а, який задає єдину модель конфігурації, режими роботи та точки розширення. Другою складовою є прикладні модулі безпеки, які реалізують перевірку вхідних і вихідних викликів, аудит та guardrails. Третьою складовою є демонстраційне середовище, що дає змогу інтегрувати starter у кілька простих мікросервісів і перевірити коректність його роботи в типових сценаріях.

## 4.2. Вибір технологій для реалізації

Вибір технологічного стеку визначався двома критеріями: відповідністю сучасній Java-екосистемі мікросервісів і сумісністю з практиками Zero Trust. Базовою платформою реалізації є Java та Spring Boot, оскільки саме ця екосистема є предметом дослідження даної роботи. Spring Boot забезпечує зручний механізм автоконфігурації, модульності та інтеграції зі Spring Security, а отже є природним середовищем для реалізації reusable starter-а.

Для побудови проєкту доцільно використати Maven. Цей інструмент дозволяє організувати багатомодульну структуру, керувати залежностями, підключити BOM для узгодження версій і формувати окремі артефакти starter-модулів. Крім того, Maven добре підходить для дослідницьких і навчальних проєктів, де важливо прозоро описати склад системи й послідовність збирання.

Ключову роль у реалізації безпеки відіграє Spring Security. Саме цей фреймворк забезпечує механізми конфігурації security filter chain, інтеграцію з OAuth2 Resource Server, роботу з JWT, методову безпеку та стандартні точки розширення для обробки помилок автентифікації й авторизації. Використання Spring Security дозволяє не створювати безпекову модель з нуля, а зосередитися на її стандартизації, автоматизації та перевикористанні.

Для реалізації метрик доцільно використати Micrometer, який є стандартом де-факто в екосистемі Spring Boot для експорту показників у Prometheus та інші системи моніторингу. Для трасування доцільно спиратися на сучасні механізми distributed tracing, інтегровані через Spring Boot спостережуваність. У частині клієнтських викликів мають підтримуватися основні засоби Spring-екосистеми, зокрема `WebClient`, `RestClient` або `RestTemplate`, а за потреби й Feign.

Інтеграція із зовнішнім сховищем секретів передбачається через Vault-сумісний підхід, але реалізація повинна залишатися достатньо абстрактною, щоб надалі не бути прив’язаною лише до одного конкретного провайдера. Для винесеної policy-based авторизації як перспективний напрям використовується Open Policy Agent, однак у межах першої реалізації цей модуль може залишатися опціональним.

Отже, обраний технологічний стек формує баланс між практичністю та дослідницькою цінністю: він спирається на реальні інструменти промислової розробки і водночас дозволяє сконцентруватися на головній меті роботи, а саме на створенні уніфікованого Zero Trust Starter для мікросервісів.

## 4.3. Організація структури проєкту

Для реалізації системи доцільно перетворити початковий каркас проєкту на багатомодульну структуру. Це дає змогу розділити ядро starter-а, прикладну безпекову логіку, інтеграції та тестове оточення. На верхньому рівні повинен бути розташований батьківський проєкт, який містить спільні налаштування Maven, узгоджені версії залежностей, конфігурацію плагінів і перелік дочірніх модулів.

До складу проєкту рекомендовано включити такі модулі:

1. `zero-trust-bom` для централізованого керування версіями залежностей.
2. `zero-trust-starter-core` для базових властивостей, валідаторів та контрактів.
3. `zero-trust-starter-security` для реалізації inbound та outbound security.
4. `zero-trust-starter-observability` для аудиту, логування та метрик.
5. `zero-trust-starter-secrets` для інтеграції з секрет-сховищами.
6. `zero-trust-starter-policy-opa` для зовнішніх policy checks.
7. `zero-trust-starter-test` для тестових анотацій і допоміжних інструментів.
8. `samples` для демонстраційних мікросервісів.

Така структура дозволяє підтримувати принцип модульності і не змушує кожен сервіс підключати зайві залежності. Наприклад, якщо конкретний проєкт потребує лише JWT Resource Server, прокидання токена та базовий аудит, йому не потрібно тягнути модулі для Vault або OPA. Водночас спільне ядро забезпечує єдиний стиль конфігурації та однакову поведінку в усіх сервісах.

У межах демонстраційного середовища доцільно створити щонайменше два мікросервіси. Перший сервіс виступає цільовим ресурс-сервером і містить захищені endpoint-и. Другий сервіс виступає ініціатором міжсервісного виклику й демонструє, як starter зберігає контекст безпеки в ланцюжку запитів. За потреби до цього середовища може бути доданий gateway, однак для першої практичної ітерації він не є обов’язковим, оскільки основний акцент роботи зроблено на application-level security, а не на edge-рівні.

## 4.4. Реалізація ядра starter-а

Базовий модуль `zero-trust-starter-core` є фундаментом усієї системи, оскільки саме в ньому зосереджуються спільні механізми конфігурації, валідатори та контракти взаємодії між модулями. У практичній реалізації цей модуль повинен містити клас властивостей, наприклад `ZeroTrustProperties`, який відображає єдину конфігураційну модель starter-а. Через цей клас зчитуються параметри, пов’язані з inbound security, outbound security, аудитом, інтеграцією із секретами, режимами роботи та guardrails.

Крім властивостей, у модулі `core` необхідно реалізувати енум або подібний механізм для підтримки режимів роботи системи, наприклад `STRICT`, `BALANCED` і `DEV`. Це дає змогу прив’язати політику fail-fast перевірок до конкретного сценарію використання. Так, у production-подібному режимі система повинна бути значно жорсткішою до небезпечних налаштувань, ніж у локальному девелоперському середовищі.

Ще однією важливою частиною ядра є підсистема валідації конфігурації. Практична реалізація цього механізму може ґрунтуватися на окремому сервісі стартової перевірки, який аналізує налаштування ще до ініціалізації основної безпекової логіки. Якщо система працює у строгому режимі та виявляє відсутність issuer URI, надто широкі публічні шляхи або наявність відкрито заданих секретів, запуск застосунку повинен завершитися з пояснювальним повідомленням. Таким чином, fail-fast стає не декларативною вимогою, а реальною частиною runtime-поведінки.

Окрім цього, у модулі `core` доцільно зосередити спільні моделі подій безпеки, контракти для публікації audit events, інтерфейси для визначення tenant-контексту та abstractions для роботи із сервісними токенами й секретами. Така організація забезпечує узгодженість між модулями і дозволяє розширювати starter без порушення вже побудованої архітектури.

## 4.5. Реалізація підсистеми вхідної безпеки

Модуль `zero-trust-starter-security` реалізує центральну функціональність системи, а саме контроль доступу до вхідних HTTP-запитів. На практиці ця реалізація повинна будуватися навколо автоматичного створення `SecurityFilterChain`, який активується за наявності відповідних залежностей і властивостей starter-а. Саме цей ланцюг задає загальну політику безпеки сервісу.

Ключовим рішенням є налаштування режиму deny by default. У межах реалізації всі запити мають вважатися забороненими, окрім тих, що явно описані як public paths або проходять повний цикл перевірки автентичності й авторизації. Така реалізація мінімізує ризик випадкового відкриття endpoint-ів у разі появи нових контролерів або змін у бізнес-логіці.

Автентифікація вхідних запитів здійснюється через JWT Resource Server. Starter має автоматично конфігурувати декодер токенів, механізми валідації issuer, audience та строку дії, а також перетворення claims у набір authorities. Однією з головних переваг цього підходу є те, що однакові правила мапінгу прав доступу можуть бути централізовано закладені в starter і не дублюватимуться в кожному сервісі окремо.

Після етапу автентифікації реалізується авторизація. Базовий рівень авторизації доцільно реалізувати через конфігураційні правила доступу до шляхів. Наприклад, шляхам адміністративного рівня відповідає роль `ADMIN`, шляхам внутрішнього сервісного обміну роль `SERVICE`, а основні бізнес-ресурси доступні будь-якому автентифікованому користувачу. Для складніших сценаріїв стартер повинен містити повторно використовувані шаблони ABAC-перевірок, зокрема перевірку відповідності tenantId або userId атрибутам запиту.

Реалізація обробки security-помилок повинна бути уніфікованою. Замість того щоб кожен сервіс формував власні відповіді на `401 Unauthorized` і `403 Forbidden`, starter централізовано надає власні entry point та access denied handler, які формують однаковий JSON-відповідь. Це спрощує інтеграцію з фронтендом, журналювання й аналіз помилок.

Не менш важливою частиною реалізації є встановлення безпечних HTTP-параметрів. У security filter chain повинні централізовано налаштовуватися заголовки захисту, політика CORS та поведінка CSRF. Для stateless API на основі bearer token логічним є вимкнення CSRF, однак ця дія має бути явною і керованою конфігурацією, щоб поведінка системи залишалася передбачуваною та задокументованою.

## 4.6. Реалізація підсистеми вихідної безпеки

Наступним важливим напрямом реалізації є підтримка міжсервісних викликів. У багатьох випадках сервіс після успішної перевірки вхідного запиту повинен звернутися до іншого мікросервісу. Якщо при цьому контекст автентифікації не буде переданий далі, наступний сервіс втратить інформацію про суб’єкта доступу, а отже ланцюг Zero Trust перевірки буде розірваний.

Щоб уникнути цього, модуль `zero-trust-starter-security` повинен містити механізми автоматичного прокидання токена. Реалізаційно це доцільно зробити через інтерцептори для HTTP-клієнтів. Коли сервіс виконує вихідний виклик і в `SecurityContext` міститься поточний bearer token, starter автоматично додає його в заголовок `Authorization` нового запиту. За аналогією також додаються технічні заголовки для кореляції викликів, наприклад trace identifier або окремий correlation ID.

Однак у практичній системі трапляються ситуації, коли вихідний виклик виконується не від імені користувача. Для таких випадків потрібно реалізувати підсистему service-to-service authentication. Найбільш придатною для першої версії є підтримка моделі `client_credentials`, коли сервіс отримує окремий access token як машинна сутність і використовує його для звернення до інших сервісів. Додатково у проєктній архітектурі доцільно передбачити можливість token exchange або використання сервісного токена, отриманого із секрет-сховища.

Підсистема вихідної безпеки має бути достатньо гнучкою, щоб дозволяти вибір стратегії автентифікації на різних рівнях. У найпростішому випадку сервіс може глобально працювати в режимі прокидання user token. У складніших випадках окремі клієнти або типи викликів можуть використовувати власну конфігурацію service token provider. Саме така гнучкість робить starter придатним не лише для демонстраційних проєктів, а й для більш наближених до реальних production-сценаріїв систем.

Окрему роль у реалізації відіграє контроль транспортної безпеки. Хоча mTLS зазвичай забезпечується інфраструктурою, starter може контролювати базові умови безпечного виклику: перевіряти використання HTTPS, сигналізувати про спроби звернення до небезпечних endpoint-ів через відкритий транспорт і, за необхідності, надавати hooks для кастомних SSL-конфігурацій.

## 4.7. Реалізація аудиту та спостережуваності

Модуль `zero-trust-starter-observability` реалізує спостережуваність безпеки як невід’ємну частину Zero Trust. На практиці це означає, що ключові security-події не повинні залишатися прихованими всередині фільтрів безпеки, а мають бути доступні для централізованого аналізу. Саме тому в модулі реалізується механізм формування й публікації уніфікованих audit events.

У межах реалізації необхідно фіксувати щонайменше такі події: успішна автентифікація, невдала автентифікація, відмова в доступі, використання сервісної ідентичності, спрацювання fail-fast guardrails та інші значущі безпекові ситуації. Для кожної події формується структурований запис з технічними й контекстними полями, які можуть бути використані в централізованих лог-системах.

Важливо, щоб реалізація аудиту не перетворювалася на неконтрольоване логування всього підряд. Тому в стартері доцільно передбачити окремий механізм маскування чутливих даних. Bearer token-и, паролі, секрети, приватні дані користувача та інша критична інформація не повинні потрапляти до журналів у відкритому вигляді. Така вимога є принциповою, оскільки погано реалізований аудит сам може стати джерелом уразливостей.

Окрім логів, модуль observability має формувати безпекові метрики. Практична реалізація цього підходу може ґрунтуватися на `MeterBinder`, який реєструє лічильники невдалих автентифікацій, відмов доступу, спрацювань guardrails, успішних прокидань токенів та помилок отримання service token. Такі метрики дозволяють оцінювати не лише факт роботи системи, а й її безпековий стан у часовому вимірі.

Ще одним важливим аспектом реалізації є зв’язування security-подій із трасуванням запитів. Для цього в журналах та помилках мають фіксуватися trace identifier і correlation context. У результаті адміністратор або дослідник може пов’язати конкретну помилку `403` із повним ланцюжком міжсервісних викликів і проаналізувати, на якому рівні відбулося блокування.

## 4.8. Реалізація роботи із секретами та конфігураційними guardrails

Модуль `zero-trust-starter-secrets` розширює функціональність starter-а за рахунок контролю над джерелами секретів і виявлення потенційно небезпечних конфігурацій. На рівні реалізації ключовим є створення абстракції постачальника секретів, яка дозволяє звертатися до зовнішнього сховища без жорсткої прив’язки до конкретного провайдера.

У межах першої ітерації найдоцільніше реалізувати інтеграцію з Vault-сумісним підходом, при якому секрети шукаються в стандартизованих шляхах, прив’язаних до назви застосунку та середовища виконання. Це створює єдиний шаблон роботи з секретами в межах усіх сервісів і зменшує кількість хаотичних локальних рішень.

Разом із тим практична цінність модуля `secrets` полягає не лише в отриманні секретів, а й у запобіганні помилковим практикам. Для цього starter має перевіряти конфігураційні файли та середовищні налаштування на наявність потенційних plaintext secrets. Якщо в конфігурації виявлено властивості, що виглядають як паролі, токени або API-ключі, система повинна відреагувати відповідно до обраного режиму. У девелоперському середовищі це може бути попередження, а в суворому режимі блокування запуску.

Guardrails мають бути реалізовані не лише для секретів. Як уже зазначалося в попередньому розділі, важливо контролювати наявність issuer URI, надто широкі public paths, permissive CORS і відсутність аудиту в production-конфігурації. Усі ці перевірки доцільно централізувати в окремому механізмі стартової перевірки, який працює ще до обробки перших HTTP-запитів.

Така реалізація перетворює starter з простої бібліотеки зручностей на активний механізм захисту, здатний виявляти помилки конфігурації до того, як вони перетворяться на реальний ризик безпеки.

## 4.9. Інтеграція starter-а в прикладний мікросервіс

Однією з цілей реалізації є мінімізація кількості дій, необхідних для підключення starter-а в новий сервіс. З практичної точки зору інтеграція повинна зводитися до трьох основних кроків: підключення відповідних залежностей, задання конфігурації в application-файлі та, за необхідності, додавання локальних правил доступу до специфічних endpoint-ів.

Після підключення starter-а мікросервіс автоматично отримує безпечну стартову конфігурацію. Якщо для сервісу ввімкнено inbound security, він починає працювати як JWT resource server. Якщо ввімкнено observability, сервіс автоматично формує audit-події та метрики. Якщо активовано outbound security, міжсервісні виклики починають зберігати контекст безпеки. Завдяки цьому інтеграція сприймається як підключення готової платформи безпеки, а не як черговий набір локальних фрагментів конфігурації.

Для демонстрації доцільно використати два прості сервіси. Перший сервіс містить захищений API, який доступний лише за наявності валідного токена. Другий сервіс приймає запит від користувача, а потім звертається до першого сервісу, автоматично передаючи токен далі. Такий сценарій дозволяє перевірити одразу кілька критичних механізмів: inbound JWT validation, рольову авторизацію, token propagation, аудит і роботу guardrails.

Інтеграція starter-а в прикладний сервіс також важлива з дослідницької точки зору, оскільки саме вона дозволяє оцінити, наскільки зменшується обсяг ручної security-конфігурації та чи справді досягається ефект стандартизації.

## 4.10. Тестування реалізації

Для системи такого типу тестування є не другорядним, а критично важливим етапом реалізації. Оскільки starter впливає на базову поведінку сервісу, будь-яка помилка в його автоконфігурації або guardrails може призвести або до небезпечної деградації захисту, або до помилкового блокування легітимних запитів. Саме тому тестова стратегія повинна охоплювати як модульні, так і інтеграційні перевірки.

На рівні модульного тестування доцільно перевіряти роботу валідаторів конфігурації, перетворення claims у authorities, логіку визначення tenant-контексту, поведінку secret detectors та формування уніфікованих error response. Такі тести дозволяють ізолювати окремі алгоритмічні частини системи і перевірити коректність їх роботи без підняття повного Spring-контексту.

На рівні інтеграційного тестування необхідно перевіряти поведінку starter-а в реальному Spring Boot оточенні. Зокрема, потрібно підтвердити, що сервіс не стартує без критичних параметрів JWT validation, що public paths справді доступні без токена, а захищені endpoint-и повертають `401` або `403` у відповідних ситуаціях. Окремо слід тестувати прокидання токена в міжсервісних викликах, генерацію audit-подій, інкрементацію security metrics і реакцію системи на небезпечні конфігураційні умови.

Для прискорення перевірок доцільно реалізувати окремий тестовий модуль starter-а, який надає mock JWT, допоміжні анотації та готові засоби ініціалізації security context. За потреби інтеграційне тестування може бути розширене за рахунок Testcontainers, якщо в системі потрібно перевіряти взаємодію з зовнішнім IdP, Vault або policy engine.

## 4.11. Очікувані практичні результати реалізації

Запропонований підхід до реалізації дозволяє отримати систему, яка не лише формально відповідає концепції Zero Trust, але й робить її застосування практичним у середовищі Spring Boot мікросервісів. Основний практичний результат полягає в тому, що безпека переходить із площини ручних локальних домовленостей у площину уніфікованого reusable-компонента.

Після завершення реалізації starter повинен забезпечувати скорочення обсягу шаблонного security-коду в сервісах, однакову поведінку при перевірці токенів, консистентний формат журналювання, спільні підходи до аудиту та конфігураційної безпеки, а також контроль за дотриманням критичних вимог через механізм fail-fast. У контексті дипломної роботи це створює хорошу основу для подальшого експериментального порівняння базового мікросервісу без starter-а і сервісу, побудованого з використанням запропонованого рішення.

Крім того, реалізація в такому вигляді відкриває шлях для подальших розширень. Зокрема, надалі система може бути доповнена глибшою інтеграцією з Vault, OPA, token exchange, підтримкою SPIFFE/SPIRE або адаптацією до service mesh. Проте навіть базова версія вже дозволяє продемонструвати головний внесок роботи, а саме можливість вбудувати принципи Zero Trust у сам механізм створення мікросервісів.

## 4.12. Висновки до розділу

У цьому розділі було розглянуто практичні аспекти реалізації системи Zero Trust Starter для Spring Boot мікросервісів. Було обґрунтовано вибір технологій, запропоновано багатомодульну структуру проєкту, описано реалізацію ядра starter-а, підсистем вхідної та вихідної безпеки, аудиту, роботи із секретами та механізму конфігураційних guardrails.

Окрему увагу приділено інтеграції starter-а в прикладні сервіси та тестуванню, оскільки саме ці аспекти дозволяють оцінити практичну придатність запропонованого рішення. У результаті сформовано цілісне бачення того, як архітектурна модель Zero Trust Starter може бути перенесена у реальну програмну реалізацію.

Таким чином, реалізація системи спирається на принципи модульності, автоконфігурації, безпечних значень за замовчуванням і контролю небезпечних конфігурацій. Це створює підґрунтя для наступного етапу роботи, а саме для побудови прототипу, проведення експериментальної перевірки та оцінювання ефективності запропонованого підходу.
